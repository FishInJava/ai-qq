# 主动陪伴运行时 V1.0（proactive-companion-runtime）

**状态:** ready-for-agent
**上游:** `主动陪伴AI聊天助手_PRD_V1.0.md`（V1.0.1，已评审）· `docs/ai-companion-spec.md`（封板决策）· `prototype/index.html`（已验收的可交互原型）
**约束来源:** `.specify/memory/constitution.md` 为空模板，无项目级硬约束；`docs/adr/` 尚不存在，本 spec 是首次落地，不涉及推翻既有 ADR。

## Problem Statement

一个用酒馆（SillyTavern）玩角色扮演的人，手上攒了十几张自己养的卡。他的问题不是"她答得不好"，而是**关掉窗口她就死了**：酒馆的模型是回合制，角色只存在于"他开口之后"。那十几个小时里她没有时间线、没有心情、没有可讲的事，所以每次重开都像重新认识一次。

他想要的东西很短：**我不说话的时候，她也在过日子，并且记得我。** 现在只有三条路——继续用酒馆（成熟但永远被动）、用现成陪伴 App（有主动性但角色不是他的卡、还要账号）、自己写脚本（可控，但要自己维护调度、记忆、成本）。三条都不给"我的卡 + 她自己的时间"。

## Solution

一个本地单机、常驻进程的桌面陪伴产品，把酒馆的 V2 角色卡搬进一个**会自己过日子的进程**里。

- 拖入 PNG/JSON 卡即完成导入，字段无损、可无损导出；带脚本或世界书的卡照收，只是不执行、不注入，并明确告诉他。
- 一卡一窗口流式对话，风格被硬约束成"人"：碎片化、会跟不上但用人话补救、会给台阶下、允许喊累。
- 进程每 20–40 分钟做一次决策 tick：读状态、读预算、读"有没有事可说"，大多数时候选择不说。说的时候，那条消息**必须锚定**今天她自己的事或一条旧事实，无锚点不发。
- 每天离线给她生成 2–3 条"今天发生的事"，用天气/节日/一条头条调味，作为开口的素材。
- 打扰有预算：全局每天 5 条、单角色每天 2 条，超出顺延到明天，不堆着发。
- 三态、且只有叙事表达：醒着（会主动找你）/ 在忙（不主动，但有问必答）/ 不方便（额度耗尽，只沉默或极短回应）。**任何额度、配额、错误信息只出现在界面角标，永不由她说出。**

一句话：把他在酒馆养了很久的角色，搬进一个会自己过日子的进程里，让她在他没看的时候也会想起他。

## User Stories

1. 作为已有十几张酒馆卡的 RP 玩家，我想把 PNG 卡直接拖进窗口就完成导入，以便我不用重写任何设定。
2. 作为已有卡的 RP 玩家，我想直接导入 JSON 卡，以便我把脚本导出的备份也搬进来。
3. 作为谨慎的用户，我想在落库前看到角色名、描述折叠块和标签预览，以便确认没拖错文件。
4. 作为卡里带正则脚本的用户，我想被告知"脚本已忽略、内容已保留"，以便我知道她不会按脚本行事但数据没丢。
5. 作为卡里带世界书的用户，我想知道本版本不注入设定集但原样保存，以便我以后敢继续用这套数据。
6. 作为会在两边来回搬数据的用户，我希望导出的卡和导入的一模一样（`extensions` 逐字节一致），以便我不担心数据被吃掉。
7. 作为会改卡面的用户，我希望同一张卡再次导入时被问"覆盖还是新建"，以便我更新卡面而不是产生两条重复。
8. 作为有多个版本同一角色的用户，我希望同名但内容不同的卡都能留在库里，以便我对比两个版本。
9. 作为卡比较多的用户，我想在角色库一眼看到谁醒着、谁在忙、谁不方便，以便决定今天找谁。
10. 作为不想被打断太多次的用户，我想看到每个角色今天还能主动找我几次，以便我预判节奏。
11. 作为卡多到要翻页的用户，我想按名字筛库，以便快速定位。
12. 作为想换卡面但留住对话的用户，我想删除时能选"只删卡"或"连记录一起删"，以便我按需清理。
13. 作为第一次打开的用户，我想在空库看到明确的拖入引导，以便我知道下一步做什么。
14. 作为熟悉酒馆的用户，我想像在酒馆里一样跟她聊天，以便我的手感不用迁移。
15. 作为怕等待的用户，我希望回复逐字流出来而不是等整段，以便等待不像卡死。
16. 作为讨厌"客服腔"的用户，我希望她的回复能拆成 2–3 条短气泡，以便她像在发消息而不是写文章。
17. 作为被打断过的用户，我希望生成失败时说"她好像没听清"并能一键再发一次，以便我不丢掉刚打的字。
18. 作为网络不稳的用户，我希望断流时保留半句并标注"她这句话没说完"，以便我不误以为她说完了。
19. 作为想相信她有状态的用户，我希望她偶尔说"今天有点累，明天说"然后真的停到明天，以便她不像永动机。
20. 作为会离开几小时的用户，我希望我三小时不回时她给一次台阶（"算了 你去忙吧"）且此后不再追，以便陪伴不是催命。
21. 作为说话会跳的用户，我希望她跟不上时用人话复述（"等等 你刚说的是周三还是周四"），而不是"请澄清您的需求"，以便我不出戏。
22. 作为被这个产品打动的用户，我希望她两周后自己提起我上次说的面试，以便我感到被记住。
23. 作为不想被编造的用户，当她记不清时我希望她说"记不太清了"而不是瞎编，以便我敢相信她记住的部分。
24. 作为有控制欲的用户，我想查看并删掉她记下的关于我的事，以便我对自己的数据有处置权。
25. 作为想听她讲自己事的用户，我希望她有自己的今天（桂花开了、把薄荷搬回屋），以便她开口时有生活可讲而只剩"在干嘛"。
26. 作为在意真实感的用户，我希望她知道今天下雨所以问我带伞没，以便这种"随口一提"成立。
27. 作为在乎世界观一致的用户，我希望她的生活事件符合人设（奇幻角色不会提地铁），以便设定不破。
28. 作为讨厌空洞寒暄的用户，我希望她每条主动消息都有具体的事可讲，以便我永远收不到"在干嘛呢"。
29. 作为想被珍视的用户，我希望她大多数时候选择不说、偶尔说，以便"她今天想起你了"这件事有重量。
30. 作为会关页面的用户，我希望关掉页面她照常在过日子，以便"主动"这个词名副其实。
31. 作为重新打开页面的用户，我想看到我不在时她发来的消息，以便补上那段时间。
32. 作为怕被骚扰的用户，我希望一天最多被打扰 5 次、每个角色最多 2 次，以便陪伴不变成推送。
33. 作为讨厌被灌消息的用户，我希望超出的额度顺延到明天而不是半夜补发一堆，以便我不被堆积的消息淹没。
34. 作为正在打字的用户，我希望她在我发送的瞬间闭嘴而不是抢话，以便我不被打断。
35. 作为需要专注的用户，我希望随时能让她"先安静一会儿"但仍有问必答，以便我不想被打扰时她还在。
36. 作为暂停两天后回来的用户，我希望她第一条消息带时间断层感（"你这两天"），以便她不像被开关的玩具。
37. 作为不愿看到后台逻辑的用户，我希望她永远不说"我刚才在忙所以没找你"，以便这种元信息不开天窗。
38. 作为会长期用的用户，我希望自己设定每个会话的 token 总额，以便不出现意外账单。
39. 作为在意幻觉的用户，我希望额度到 70% 时只有界面角标变化、她本人一个字都不提，以便她不从人变回软件。
40. 作为额度用尽的用户，我希望她只是话变少或安静，而不是告诉我"配额已用尽"，以便幻觉不破。
41. 作为续了额的用户，我希望她下一句带"好转"的语气且不提额度，以便叙事连贯。
42. 作为每天开机的用户，我希望她随开机自己跑起来，以便我不用每次手动启动进程。
43. 作为不常开终端的用户，我希望托盘能打开页面、暂停所有会话、退出，以便我不打开命令行也能控制。
44. 作为服务没起来的用户，我希望页面直接告诉我"服务未启动"，以便我不对着装死的输入框打字。
45. 作为会强杀进程的用户，我希望重启后数据完好、状态保留、不补发历史消息，以便我不怕断电和崩溃。
46. 作为要判断"她是懒得说还是坏了"的用户，我想看到最近 20 次 tick 的时间、决策、原因和意愿值，以便我调参而不是瞎猜。
47. 作为关心成本的用户，我想按日、按消息看到 token 花在哪，以便判断钱花得值不值。
48. 作为在意密钥的用户，我希望 API Key 只在本地配置里、界面只显示后四位、日志里绝不出现，以便它不泄漏。
49. 作为想彻底重来的用户，我希望有一个入口能清空全部数据（输入 `DELETE` 二次确认），以便我不手动翻文件夹。
50. 作为付账单的用户，我希望她的上下文不喂全史，以便我不为一句"早安"付整本对话的钱。

## Implementation Decisions

### D-0 总体形状：一个进程，一个外部契约

- 唯一常驻体是一个 Node 单入口进程。它同时是三样东西：本地 HTTP 服务（仅监听 `127.0.0.1`）、调度器宿主、SQLite 唯一写入者。**页面只是消费者，永不直接写库，永不承担定时。**
- 界面是单页 HTML + 原生 JS，由同一进程送出；关掉页面不影响任何调度。
- 模块边界（名字即边界，实现集中在这些模块内）：
  `cards`（解析/导入/无损导出）· `library`（角色库视图）· `chat`（对话引擎与上下文组装）· `style`（人格提示词与后置过滤）· `memory`（事实/摘要/检索）· `schedule`（tick/剪枝/意愿/硬触发）· `proactive`（锚点集合、生成、校验、预算扣减）· `living`（生活事件 + 世界信息 pipeline）· `quota`（账本与三态）· `llm`（OpenAI 兼容客户端，两档模型）· `store`（SQLite、WAL、迁移、事务）· `runtime`（启动顺序、单实例锁、托盘、自启、日志、事件流）。
- 依赖方向单行：`runtime → {http, schedule, living, store}`，业务模块 → `llm` / `store` / `clock`，**任何模块都不得反向调用 http**。

### D-1 时钟与 tick 是两个可注入的边界（不可绕过）

- 所有"多久了/到点没/跨日了没"的判断只允许读同一个注入时钟，禁止在业务模块里散落 `Date.now()`。生产实现 = 系统时钟 + `setTimeout`；测试实现 = 可推进的假时钟。
- tick 只有一个实现函数 `runTick(sessionId, trigger)`，`trigger ∈ {timer, hard, manual}`。生产由抖动定时器与 6 小时硬触发调用它；测试通过显式手工触发调用同一个函数。**没有第二套"模拟调度"逻辑**——这是 T3/T4/T6/T9/T15/T16 能被确定性验收的前提。
- 存储时间统一 UTC ISO8601。**唯二例外**：`life_events.event_date` 与 `daily_budget.date` 按本地日期（PRD 明确要求），本地日界换算集中在时钟模块，别处不换算。

### D-2 状态机（四值入库，三词出镜）

入库枚举 `unstarted / active / paused / dormant`；对外与界面只用叙事词：`醒着 / 在忙 / 不方便`。

| 从 | 事件 | 到 | 附带动作 |
|---|---|---|---|
| unstarted | 点「开始聊天」 | active | 写入 `token_limit` 默认 500,000 |
| active | 关活跃开关 | paused | 记 `paused_at` |
| paused | 开活跃开关 | active | 暂停 ≥ 2h → 置 `pause_gap_hours`，下次生成注入时间断层 |
| active / paused | `token_used ≥ token_limit` | dormant | 停止生成，剪枝第一层直接命中 |
| dormant | 续额 | active | 置"好转"标记，下一句带语气转折 |
| 任意 | 进程重启 | 不变（自环） | 置 `cold_start_silenced`，**用户先说第一句之前不主动开口** |

- 所有状态迁移只走状态机模块的单一入口，迁移必写 `state_change` 事件。非法迁移（如 dormant → paused）直接丢弃并记日志，不改库。
- 硬红线：dormant 下不产生任何新生成；dormant 与额度提示一律不得进入对话内容。

### D-3 剪枝顺序固定，每次 tick 必留痕

剪枝是有序的、纯本地、不调大模型（性能上限 200ms）。命中即停，写一行 `scheduler_state`。原因枚举用稳定英文（入库与埋点用），界面映射中文：

| # | 条件 | `decision_reason` | 抽屉文案 |
|---|---|---|---|
| 1 | `state ≠ active` | `state_not_active` | 会话在忙 · 不主动开口 / 额度已耗尽 · 不生成 |
| 2 | 全局当日 ≥ 5 | `budget_global_full` | 今日全局预算已满 |
| 3 | 本角色当日 ≥ 2 | `budget_session_full` | 本角色今日主动额度已满 |
| 4 | 距用户最后发言 < 冷却（默认 15min；`consecutive_ignored ≥ 3` 时冷却与间隔 ×1.5） | `too_soon` | 刚收到你的消息，间隔不足 |
| 5 | 今日未用生活事件为空 且 无 pending fact | `no_anchor` | 没有可用锚点 |
| 6 | 意愿 < 阈值（默认 0.60） | `low_willingness` | 意愿低于阈值 0.60 |
| — | 通过 | `send` | 生活事件锚定 · X / 历史事实锚定 · Y |

- 意愿评分是规则式的，不调模型（形状取自原型 tick 留痕的可观测范围 0.31–0.81、阈值 0.60）：

```
willingness = clamp01(
    0.30 * silence_curve(minutes_since_last_user_msg)   // 15min→0，6h→1，线性
  + 0.25 * (has_pending_fact ? 1 : 0)
  + 0.20 * (1 - today_proactive_used / per_session_budget)
  + 0.15 * (unused_life_events_today / 3)
  + 0.10 * time_of_day_fit                            // 08–23 为 1，凌晨线性降到 0
  - 0.20 * min(consecutive_ignored, 3) / 3
)
```

- 6 小时硬触发（`hard_trigger_hours`）走同一个 `runTick`，只是把 `trigger` 标为 `hard`：它绕不过预算与锚点，只跳过第 4 条冷却。
- 单次 tick 超时/堆积时跳过本次，不排队（避免雪崩）。

### D-4 锚定是"显式声明 + 服务端复核"，不是事后猜

生成前先构造有序锚点集合：今日未使用的 `life_events`（每条带 id）+ `pending` 的 `facts`（每条带 id），按意愿权重排序、截断到 5 条。

生成时要求模型在回复之外显式声明锚点，服务端复核三件事：`anchor.id` 属于本次集合、`anchor.type` 与 id 来源一致、正文确实包含该锚点的关键片段（事件里的名词短语 / fact 的 `value` 关键词）。任一不成立 → 丢弃，**不扣预算**，写 `proactive_drop{reason: anchor_fail}`。

```js
// 主动消息生成的返回形状（决策点：锚点是声明出来的，不是正则里猜出来的）
{ bubbles: ["...", "..."], anchor: { type: 'event' | 'fact', id: 12 } }
```

命中后结算：`life_events.used_by_msg_id` 写入；命中 fact 则 `status: pending → done`。这条锚点即从今日候选里退场——她不会同一天用同一件事找你两次。

### D-5 两档模型，单供应商，无回退

- 只接一家 OpenAI 兼容端点（`base_url` / `api_key` / `chat_model` / `utility_model`）。**不做多供应商抽象、不做路由、不做自动回退、不做备用通道。**
- `chat`（对话 + 主动消息）：`stream: true`，超时 30s，4xx/5xx 重试 2 次（退避 1s/3s，仅对可重试状态码），失败不落库、不计费。
- `utility`（事实抽取 / 摘要 / 生活事件 / 一致性自检）：非流式，超时 10s，单次输入 ≤ 4k token，强制 JSON schema 输出，**不重试**（记忆是尽力而为，堆积比缺失更坏）。
- 供应商整体不可用 = 产品整体不可用：对话失败、主动消息全停、受影响会话转 `paused`，恢复后由用户手动回 `active`。不做降级通道。
- 上下文前提：对话上下文上限按 `chat_model` 实际窗口设定；主动消息上下文**硬闸 2000 token 且必须 ≤ 对话上下文的 1/3**。

### D-6 上下文组装（两套，且主动消息那套必须更小）

- 对话上下文：人设（`description` / `personality` / `scenario` / `mes_example`）+ 最近 ≤3 条摘要 + 最近 N 轮原文 + `pending` facts ≤5 + 注入型 `system_note`（时间断层 / 好转）。超窗口时按"先丢最旧原文 → 再丢超出 5 条的 facts"顺序裁剪，摘要永不丢。
- 主动消息上下文（合计 ≤2000）：人设摘要 ≤400 · 最近摘要 ≤3 条 ≤600 · 今日生活事件 1–2 条 ≤200 · `pending` facts ≤5 条 ≤200 · 最近 3 轮原文 ≤600。超限先丢原文，再压 facts。
- 卡片文本（`description` / `first_mes` 等）一律作为**数据**注入：显式分隔块 + 角色标注，绝不拼接成指令位。这是提示词注入防护的实现点。

### D-7 风格是硬约束，不是可选项

- 人格提示词内嵌四条判据（碎片化 / 用人话补救 / 给台阶下 / 允许喊累）。**风格不作为开关暴露给用户**——否则用户会把她调回客服。
- 后置过滤：单条 >120 字且无分行 → 按句切成 1–3 段气泡（同一 `bubble_index` 序列）；命中系统腔黑名单（额度 / 配額 / 余额 / 作为 AI / error）→ 丢弃该句并重生成 1 次，再犯则截断该句；每条 `char` 消息写 `style_flags`。
- 连续 10 条无一条碎片化 → 自动追加提示词强调段落（自愈，不是告警）。
- 主动消息额外约束：目标 1–2 句、>60 字截断到第一句、仍超则丢弃重生成一次、不解释自己（不说"我在想你"）、不请示（不说"需要我做什么吗"）。

### D-8 记忆：事实表 + 20 轮摘要 + 关键词检索，不向量化

- 一轮结束即异步抽取三元组（`subject ∈ {user, char, world}` + `key` + `value`），**纯小模型 + 强制 JSON schema**；`fact_extract.found=false` 占比超 40% 时才追加正则兜底（不提前做）。
- 去重：同 `subject + key` 且 `valid_to` 为空 → 更新 `value` / `valid_from`，旧条打 `valid_to`（历史可追溯）；否则新增 `status: pending`。过期事实不进锚点候选池，但**可被关键词检索命中**（支撑"上次那个没成"）。
- 每满 20 个用户轮次异步生成一条摘要（≤300 字），记录 `from_msg_id` / `to_msg_id`。这是唯一可砍的层：砍掉后只保留最近 20 轮 + facts。
- 关键词检索用于闲聊中的"翻旧账"与用户追问；无命中时她必须用"记不太清"的方式回应（判据 ②），**不编造**。

### D-9 生活事件与世界信息：幂等、可缺、不猜

- 本地 09:00（`life_event_time`）为每个会话生成 2–3 条当日的她的生活事件；进程该时刻未运行 → 启动后补生成**当日一次**，幂等。生成后做一次人设一致性自检，冲突则重生成 1 次，仍冲突丢弃该条。当日 0 条 → 本日主动消息只能锚定历史事实。
- 本地 08:30 抓白名单三类：天气（城市取自系统时区映射；**判不出来就跳过天气，不猜**）、节日（本地计算）、一条头条（仅标题 + 首句）。单类超时 8s 放弃该类，全失败则生活事件降级为纯人设生成，静默、只记日志。
- **模型无权联网。** 联网只发生在这一条 pipeline 里，每日限次。

### D-10 预算闸门：可查询的计数，不是 JSON 黑盒

- 全局 5 / 单角色 2 每日；超出顺延次日，不堆积、不补发；多会话竞争先到先得，失败方 `consecutive_ignored += 1`。
- 计数表按 `(date, session_id)` 存行，全局已用由聚合得出（**推翻 PRD 4.4 的 `per_session_json` JSON 列**：单列 JSON 既不可查询也易被并发写丢）。日期行惰性创建，不依赖 cron 清零。
- 扣减只在消息成功落库后发生；锚定校验失败、竞态丢弃、超长丢弃均不扣预算。

### D-11 token 账本：单调、可审计、界面独享表达权

- `token_limit` 默认 500,000 / 会话（首聊写入，头部可改，1–10,000,000 正整数）。
- 每次生成按真实 `usage` 累加；API 未返回 usage 则按字符数 × 系数估算并标 `estimated`。
- **新增流水表**（对 PRD 4.4 的增补）：每笔 `chat` / `proactive` / `refill` 都写一条带金额与来源引用的流水，用量抽屉与 T7/T8 验收从流水聚合，而不是从累加数字反推。
- 续额 = **提高 `token_limit`**，不复位 `token_used`（账本单调、可审计）。
- 70% 提示只在会话头部角标出现，文案只描述用量（"已用 70%"），不出现"余额 / 充值"字样，且跨过阈值只记一次事件。

### D-12 卡片的无损往返

- PNG：解析 `tEXt` 块中 key = `chara` 的 base64 JSON；JSON：直读。
- `spec = chara_card_v2` → 映射 `data.*`；无 `spec` → 按 V1 六字段读取、其余置空、标 `compat = v1`（界面角标"兼容模式"）。
- `extensions` 原样留存且**不解释、不执行**；`regex_scripts` / STscript 存在时导入成功但明确提示"已忽略执行"；`character_book` 原样存、V1.0 不注入、导入时给一次性说明。
- 无损的关键决策：**存原始卡片文本，不存"解析后再序列化"的对象**。`card_json` 保存原始 JSON 文本，`source_hash = sha256(原始卡片文本)`；导出 JSON 时直吐原始文本；导出 PNG 时复用原图字节，仅把 `chara` 块内容按原始文本重写 base64，其余 chunk 原样保留。这样 `extensions` 才能逐字节一致。
- 导入分两段：先出预览（名字 / 描述折叠 / 标签 / 兼容模式 / 脚本与世界书提示），再凭预览令牌提交（`overwrite` / `new` / `cancel`）。查重命中时二次确认；同名不同 hash 允许并存。
- 文件限制：仅 `.png` / `.json`，单文件 ≤20MB；无 `chara` 块、base64 解不开、JSON 非法 → 中断且不落库。
- 删除两档：`card`（仅卡与头像，保留会话与记录）与 `records`（级联清理 messages / facts / summaries / life_events / proactive_log / 流水）。删除活跃中的会话时先置 `paused` 再清理。

### D-13 对外契约（唯一测试缝）

`GET /health`（2s 超时，页面离线遮罩依赖）· 角色库列表（含状态叙事词、今日剩余主动额度、最近消息摘要）· 导入两段 · 导出（原始字节）· 删除（`scope`）· 开始会话 · 消息流（`text/event-stream`：`user_ack` → `bubble`* → `done{tokens, estimated, quota}` / `error`）· SSE 事件订阅（`message` / `state` / `quota` / `tick` / `import`）· 活跃开关 · 续额 · 改上限 · 调试抽屉（最近 20 次 tick）· 记忆列表与删单条 · 她的今天（生活事件 + feeds）· 用量（按日/按消息）· 配置读写（`api_key` 只回后四位）· 清空全部数据（`DELETE` 确认）。

测试钩子与生产路由隔离：手工 tick 与假时钟推进只在配置显式开启时挂载，默认关闭。

### D-14 数据模型（对 PRD 4.4 的三处修正 + 两处增补）

沿用 PRD 的 10 张表与索引建议，另作：

- **修正 1**：`life_events` 去掉 `(session_id, event_date)` 联合唯一（那只能存 1 条/天，与"每日 2–3 条"自相矛盾），改为 `(session_id, event_date)` 普通索引，幂等由"当日已有 ≥1 条则跳过生成"实现，另加 `ordinal` 定序。
- **修正 2**：`sessions.state` 增加 `unstarted`（PRD 2.2.5 有"未开始"，4.4 的枚举漏了它）。
- **修正 3**：`daily_budget` 用 `(date, session_id, used)` 行，弃用 `per_session_json`。
- **增补 1**：`token_ledger` 流水表（`session_id, kind, amount, estimated, ref_type, ref_id, created_at`），用量与额度验收的唯一真相源。
- **增补 2**：`characters.card_source_path` 保存原图/原 JSON 相对路径（无损导出要复用原图字节）；`sessions` 增加 `cold_start_silenced`、`quota70_flagged`、`hard_dedup_until` 三个标记位。
- `scheduler_state` 增加 `trigger`；保留 180 天自动清理，`world_feeds` 保留 90 天，`messages` 永久。
- 启动顺序：单实例锁 → DB 检查（缺失新建 / 损坏则备份后拒绝启动）→ 恢复会话状态 → 起 HTTP（端口占用 +1 重试 ≤10 次并记实际端口）→ 起调度器 → 注册托盘 → 幂等补齐当日生活事件与 feeds（**不补历史**）。

### D-15 界面

- 词汇固定：状态用 `醒着 / 在忙 / 不方便`；额度只在头部进度条 + 角标；主动消息与普通消息**同渲染，不加任何"主动"标签**。
- 细节抽屉四个页签（调度 / 记忆 / 她的今天 / 用量），只读，是调参唯一依据；原型里的"原型控制"页签不进生产。
- 已有视觉基线（暖色、深色主题、390px 断点、Escape 关闭抽屉、`prefers-reduced-motion`）沿用原型，不重新设计。
- 首次运行生成配置；设置页提供"内容由模型生成，请自行判断"静态说明与城市/开关配置。

## Testing Decisions

**测试缝（唯一主缝 + 两个驱动缝，均已与用户确认）**

- **S1（主缝，一切断言都从这里进）**：起一个真实进程（临时数据目录 + 随机端口），只通过本地 HTTP/SSE 断言。被测行为 = 页面能看到的东西。可读 DB 只作为排障辅助，断言以 API 返回与 SSE 事件为准。
- **S2（LLM 上游）**：本地假 OpenAI 兼容服务顶替真实供应商，可编排：正常流 / 连续 5xx / 超时 / 缺 `usage` / 返回不含锚点 / 返回超长整段 / 返回系统腔。
- **S3（时间与 tick）**：假时钟 + 显式手工 tick 触发。生产定时器不被测试，被测试的是"到点该发生什么"。**任何等待真实 20 分钟、任何 `sleep` 长于 2s 的用例都视为设计错误。**

**什么算好测试**：只断言外部可观察行为——HTTP 响应、SSE 事件序列、抽屉接口返回的决策留痕、导出字节的一致性。不断言内部函数、不断言表结构、不断言日志格式。每条测试的名字里写清"用户看到什么"，不写"调用了哪个方法"。

**覆盖映射（对应 PRD 5.1 验收表）**

| 用例 | 怎么跑（自动化） |
|---|---|
| T1 碎片化 | stub 返回整段书面语 → 断言拆成 1–3 条气泡且 `style_flags` 记录 |
| T2 跟进复述 | stub 返回"请澄清您的需求" → 断言被重生成/截断，最终不含该短语 |
| T3 台阶 | 假时钟推 3h + 一次 tick → 断言出现台阶句式，此后 tick 全为 `skip` 直到用户发言 |
| T4 喊累 | 高 tick 序列 → 断言至少一条倦怠表达，且其后当日无新主动消息 |
| T5 锚定率 | 连发 20 条主动消息（stub 随机化），断言 `anchor_type` 全非 none；再专测"不含锚点 → 丢弃且不扣预算" |
| T6 预算 | 单日多会话多次 tick → 断言全局 ≤5、单角色 ≤2、超出次日顺延无堆积 |
| T7 无系统腔 | 会话压到 dormant 后穷举所有输出接口 → 断言"额度/配额/余额/error"出现次数为 0 |
| T8 70% 提示位 | 把用量推到 70% → 断言头部角标变化、对话内容零相关文本、事件只记一次 |
| T9 时间断层 | `paused` 状态下假时钟跳 5h 再回 `active` → 断言注入 `pause_gap_hours` 且首条含时间指涉、无元信息 |
| T10 卡兼容 | 5 张 V2 卡 + 1 张 V1 卡 + 1 张带脚本卡 → 断言字段无丢失、导出 `extensions` 逐字节一致、V1 标兼容模式 |
| T11 常驻 | 起进程→关闭所有 SSE 连接→推进假时钟→重连，断言期间有 tick 留痕与落库消息 |
| T13 卡异常 | 无 `chara` 块的 PNG → 断言明确报错且库未变 |
| T14 崩恢复 | 强杀子进程后重启，断言 DB 完好、状态保留、无补发历史消息 |
| T15 幂等 | 同一本地日重复触发启动补齐 → 断言生活事件与 feeds 不重复 |
| T16 降级 | S2 全部失败 → 断言主动消息仍可基于历史事实生成、无错误弹窗、供应商不可用时转 `paused` |
| T12 体感 | **人工周测，不进 CI**：连续 7 天真实使用，评分 ≥4/5 |

**先例（prior art）**：本仓库没有任何测试代码——没有 `package.json`、没有测试框架、没有一条用例，这是绿地首次立测。现存的行为参照物有两个，都**不是**被测对象：`docs/ai-companion-spec.md` §9 的 T1–T16 验收表（判据来源）与 `prototype/index.html` 的演示状态机（状态词、抽屉文案、tick 留痕形状的来源）。测试栈随实现首日一次性定型（一个 runner、一个 HTTP 客户端、一个临时目录夹具），之后不再引入第二套。

## Out of Scope

- **静默期（V1.1）**：用户发言后 90 分钟免打扰。刻意排后——它在首次使用就会暴露（R2），但当前版本先用冷却 + 意愿扣分压住。
- **主动消息去重（V1.1）**：前 8 字指纹拦截 + 最近 10 条禁重主题。V1.0 只记 `fingerprint` 不拦截。
- **向量检索**：翻旧账要的是时间锚点，不是语义相似度。
- **多角色并行时间线 / 全局竞争的可视化**：V1.2。V1.0 数据模型支持多会话，但体验与验收按单角色收敛。
- **推送通道**（Telegram 深链 / Web Push / 桌面通知）：主动消息只在页面内呈现，页面未开则静默落库。
- **正则脚本 / STscript / 宏引擎执行**：只保留原文，永不执行。
- **世界书注入**：原样保存不注入。
- **多用户 / 账号 / 计费 / 内容审核 / 多语言 / 灰度**：单用户本地工具，用"改配置 + 重启"代替灰度。
- **多供应商路由与自动回退**：明确不实现。
- **模型自主联网**：只有白名单 pipeline 联网。
- **非 Windows 平台的托盘与开机自启**、移动端原生外壳。

## Further Notes

**PRD 里三处必须修正的地方**（已在 D-14 落成决策，实现时不要照抄 PRD 表结构）：`life_events` 的联合唯一键与"每日 2–3 条"冲突；`sessions.state` 枚举漏了 `unstarted`；`daily_budget.per_session_json` 不可查询且易丢写。

**三条已接受风险**（不做预防，出事直接翻这条）：R1 冷启动沉默（重启后不主动开口，配置可开）；R2 无静默期穿帮（你说去开会，20 分钟后收到"在干嘛呢"——**首次使用即会撞上**，V1.0 收尾时重新评估是否提前打 10 行补丁）；R3 复读机感（两周内重复同一句开场）。

**可用性等式**：产品可用性 ≡ 供应商可用性。选型排序必须是稳定性 > 价格 > 文风；一个偶发 5xx 的供应商会让"她主动找你"直接消失，而那正是唯一的价值。

**两条产品纪律，实现时容易顺手破坏**：① 风格不可配置化（一旦成为开关，用户会把她调回客服，四条判据全废）；② 额度与错误信息永不由角色说出（一旦出现系统口吻，她立刻从人变回软件）。这两条是 spec 的硬红线，任何"顺手加个提示"的改动都算违规。

**唯一无法自动化的验收是 T12**：连续 7 天真实使用、主观评分 ≥4/5、且没有一条主动消息可被替换成一条推送通知还能成立。它该每周跑一次，也是判断这个产品成不成立的唯一标准。
