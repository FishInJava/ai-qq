# /fix-bug — 修 bug 不写票

## 入口：命令只有一条

这条通道**只由 `/fix-bug` 打开**。

- 用户打了 `/fix-bug` → 进通道，不写票。
- 用户没打，哪怕你觉得「这明显是个 bug、写票太浪费」→ **不许自己切进来**。走票，或者问一句：「这条走 `/fix-bug` 还是开票？」
- 判定权在人手上。agent 不猜。

为什么这么设：靠"这句话像不像 bug"来分叉，等于让模型自由裁量，同一个请求今天走票明天不写票，通道就废了。一条斜杠命令没有歧义：打了就是，没打就不是。

## 0. 进来之后的自查（越界就停下问人）

命令打开了通道，不等于请求就合法。动手前过一遍这张表，任意一条不满足 → **停下，一句话问人**，不要自己决定继续：

| 检查 | 不满足时 |
|---|---|
| 期望行为在 spec / PRD / 原型 / 现有用例里**已经写定**（不是边修边想出来的） | 「这更像新行为，开票？」 |
| 只把实现改回约定，不引入新字段、新接口、新界面 | 同上 |
| 不碰 `docs/ARCHITECTURE.md §6` 对外契约 | 「要改契约，按 A2 问你」 |
| 不碰数据模型/迁移、不加依赖、不改 `Rule.md §8` 任何同意项 | 逐条点名问 |
| 不搬红线归属模块（`ARCHITECTURE §8`） | 「要搬归属，属于架构改动」 |
| 改动集中在一到两个相邻模块 | 「散在 3 个以上模块，多半是设计问题，转票？」 |

一次只问一个问题，带上你判断的依据（哪个文件、哪一行）。

## 1. 分支

```powershell
git switch main
git pull --ff-only origin main
git switch -c fix-<slug>          # 例：fix-startup-url-port
```

`fix-<slug>`，不带票号。分支名里出现 `ticket-` 就说明它本该是票。

## 2. 先红后绿（能测就必须测）

1. **复现**：按 `Workflow.md` §7 的分类找落点，写一条失败用例。
   - 对外行为 → `test/s1/`，用例名写用户视角的现象，不写函数名。
   - LLM 剧本 → `test/s2/`，剧本放 `test/fixtures/fake-llm/`。
   - 时间/调度/tick → `test/s3/`。
   - 跑一次，确认它**因为预期原因**红（不是语法错、不是端口占用）。
2. **测不出来**（纯文案、纯启动输出、只在人工点击时可见）：PR body 写清手动复现与验证步骤。**不许**造一条只断言常量等于自己的空壳用例。
3. **修**：最小改动。不许顺手重构别的模块、不许放宽断言阈值（`Rule.md §7-19`）。
4. **绿**：新用例转绿，原来绿的还绿。

## 3. 门禁（顺序固定，前一步红不跑后面）

```powershell
npm run check
node --test test/s1/<受影响>.test.js   # 最快反馈
npm test                                 # 全量，不许挑着跑
npm run smoke
```

判定同 `Workflow.md` §6：`check` 无输出、全量全绿、smoke 退出码 0、3 秒内起得来。

## 4. 一个 commit

一个 bug 一个 commit，不拆「先加用例再修」两步。

```
fix(<模块>): <用户看到的现象，一句话>

症状：<什么情况下发生，看到什么>
根因：<哪个文件哪一处，为什么>
修法：<改了什么，为什么这样改最小>
验证：<用例文件 + 手动步骤>
```

例：

```
fix(runtime): 端口被占用递增后仍打印配置里的端口

症状：3000 被占时进程起在 3001，控制台却仍打印 3000
根因：启动日志读的是配置值，不是 http.start() 返回的实际端口
修法：改用返回值拼地址，一处
验证：test/s1/t17-startup-url.test.js（端口 0）
```

`docs:` 之类的「关票」提交不存在在这条通道里。

## 5. 一个短 PR

`--body-file` 用下面五段，**不套** `.github/pull_request_template.md` 的七段版（那是给票用的）：

```markdown
## 症状
<用户看到什么，怎么复现，影响谁>

## 根因
<文件:行 + 一句话解释>

## 改动
<文件清单，每个一行>

## 验证
- 新增/修改用例：`test/...`
- `npm run check` 无输出 / `npm test` N/N / `npm run smoke` 退出码 0
- 手动：<点了什么，看到什么>

## 风险与回归面
<可能有副作用的地方；无则写「无，改动局限于 X」>

关联：无票（/fix-bug 通道）
```

推上去由人合并，代理不许 `gh pr merge`（`Rule.md §7-22`）。

## 6. 不产生的东西

明确不写，别好心补上：

- `.scratch/**/issues/` 下任何新文件
- 票的 `## Notes`、验收项勾选、`Status:` 变更
- 单独的 `docs: ...` 提交
- 任何「修复记录.md」「问题说明.md」这类旁路文档

记录只在三处：**commit message（为什么）、PR body（改了什么）、用例名（怎么验的）**。需要长期记住的坑写进 `Coding阶段总结.md` 一行，或代码里那段的原因注释，不另开文件。

## 7. 修到一半发现不是 bug

- 要靠新行为才能解决 → 停下，写票，PR 转 `needs-decision` 或关掉。
- spec 自身矛盾 → 按 `Workflow.md` §12.2：不改 spec，写清哪条、为什么不成立、建议改法，问人。
- 30 分钟没缩小范围 → 停，汇报现象 + 已排除的假设 + 需要人回答的一个问题（`Workflow.md` §7 最后一行）。

## 汇报格式

五段，短：改了什么 / 怎么验证 / 偏差风险 / 需要你决定 / 下一步。同 `Workflow.md` §11。
